# 02 · 素材进场：命名、扫描与缓存

## 这一篇解决什么

一堆命名混乱的素材进来，工具怎么认出「这是某剧第 3 集」？为什么扫第二遍快 3 倍？改了文件后缓存怎么失效？

**主代码位置**：`djkit/media.py`、`djkit/core.py`（`probe`、`probe_cached`、`quick_hash`）

---

## 1. 能认的命名格式

`parse_episode()` 用正则从文件名和父目录名里提取**剧名 + 集数**：

```
某剧_第03集.mp4
某剧_EP03.mp4
某剧 03.mp4
某剧-03-1080p.mp4
03.mp4          ← 放在「某剧组」文件夹里也能认
```

集数支持 `001`、`03`、`EP03`、`第3集`。认不出来时 `ep=None`，`rename` 会把它排在最后，不会瞎猜。

`clean_title()` 会去掉画质标记、来源标记这些噪声（`1080p`、`WEB-DL`、`AAC` 等），留下干净的剧名。

---

## 2. `scan`：先看清楚再动手

```bash
python -m djkit scan 素材库/ -o 素材清单.csv
```

输出控制台表格 + CSV（UTF-8 BOM，Excel 直接打开不乱码）。每条素材给出：

- 识别出的剧名、集数
- 时长、分辨率、体积
- 首尾哈希（用于查重）

**首尾哈希不是全文件哈希**：只读头尾各 1MB（`quick_hash`），快得多。40 条素材重复扫描从 2.51s 降到 0.90s 的另一个原因是 `probe_cached`。`scan`/`report` 仍算哈希，因为台账里的指纹列有用；`slice`/`fit` 不算，省掉每文件 2MB 随机读。

---

## 3. `rename`：默认只预演

```bash
python -m djkit rename 素材库/            # 只打印会怎么改
python -m djkit rename 素材库/ --apply    # 真改
```

统一成 `剧名_003.mp4`，冲突自动加 `_dup2`。改完在 `.djkit/` 留撤销记录——**不会直接删你的原文件**。

看一下 `cmd_rename` 的实现：它先把所有改名操作算完、检测冲突，再一次性执行。中途出错不会留下「一半改了一半没改」的状态。

---

## 4. `probe_cached`：缓存的正确姿势

这是整个项目用得最多的基础设施。看 `core.py`：

```python
def probe_cached(path: Path, cache: Path | None) -> dict:
    """按 路径+大小+mtime 做 key 缓存 probe 结果"""
    if cache is None:
        return probe(path)
    key = f"{path}|{path.stat().st_size}|{path.stat().st_mtime_ns}"
    ...
```

**为什么 key 里要有大小和 mtime**：只按路径缓存的话，文件被替换了你还在用旧元信息。加上 `st_size` 和 `st_mtime_ns`，文件一改 key 就变，自动失效。

缓存落在 `.djkit/probe/`，`prune_probe_cache()` 定期清理超过 30 天或超过 2 万条的条目——不清理的话，常年跑这个项目会积累几万个 JSON 小文件。

**什么时候绕开缓存**：调试时怀疑元信息不对，加 `--no-cache` 强制重新探测：

```bash
python -m djkit scan 素材库/ --no-cache
```

## 5. `Clip`：贯穿全流程的数据结构

`media.py` 的 `Clip` 是后面所有模块的输入：

```python
@dataclass
class Clip:
    path: Path
    title: str
    ep: int | None
    duration: float
    width: int
    height: int
    has_audio: bool
    ...
```

`collect()` 负责从目录生成 `Clip` 列表，`collect_args()` 把命令行参数转成 `collect()` 需要的开关。

**理解这个结构很关键**：`fit`、`slice`、`report` 都吃同一份 `Clip`，所以「识别剧名」只做一次，不需要每个命令重写一遍。

## 6. 切片：`slice` 的三种模式

```bash
# 每集开头 20 秒（投流素材常用）
python -m djkit slice 素材库/ --mode head --head 20 -o 切片/

# 每 30 秒一段（均匀覆盖）
python -m djkit slice 素材库/ --mode even --seg 30 -o 切片/

# 指定区间
python -m djkit slice 素材库/ --mode ranges --ranges "0-15,62-78" -o 切片/
```

`--copy` 快 10 倍，但**切点会吸附到关键帧**，可能差零点几秒。要精确的切点就重编码（默认）。投流素材建议重编码——差的这零点几秒经常正好切在台词中间。

输出文件名带区间信息：`剧名_EP003_p01_5s-11s.mp4`。这个 `_p01_5s-11s` 不是装饰，第 3 篇讲字幕平移时会用到：**烧字幕时工具从这里反推出「这段是从原片第 5 秒开始的」**。

## 常见坑

**剧名识别成「第」或空字符串**
文件名里集数前面的部分太短。把素材放进 `某剧/` 目录，或者手动 `rename` 成 `某剧_003.mp4`。

**扫描结果里同一集出现两次**
`scan` 的哈希查重只对完全相同的文件生效。同一集不同压制版本（1080p / 720p）会被当成两条，这是对的——后面 `fit` 会出两个规格。

**缓存目录越来越大**
`prune_probe_cache()` 会在 `scan` 时顺手清理。想手动清：`python -m djkit gui` 素材页的「清理缓存」按钮，只清白名单目录。

**改了文件但结果没变**
八成是缓存。加 `--no-cache` 验证。

---

## 小练习

1. 造三个不同命名的同剧文件（`某剧_03.mp4`、`某剧 EP04.mp4`、`某剧-05-1080p.mp4`），跑 `scan` 看识别结果。
2. 跑一次 `rename` 预演，确认没有误改，再加 `--apply`。
3. 连续跑两次 `scan`，对比耗时；第二次加 `--no-cache`，再对比。
